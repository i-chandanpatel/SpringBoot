 # Student CRUD Application — Flow and Method Notes

 ## 1\. Application Overview
 This application is a Spring Boot REST API for managing `Student` records.
 The application follows a layered structure:


Client
  |
  | HTTP Request
  v
StudentController
  |
  | calls methods
  v
StudentService
  |
  | calls repository methods
  v
StudentRepository
  |
  | communicates with database
  v
Database


 There are three important layers in the code provided:

- **Controller** — receives HTTP requests and sends HTTP responses.
- **Service**  — contains the application's business logic.
- **Repository** — communicates with the database.

 The `Student` entity represents the actual student data stored in the database.




 # 2\. Request Flow

 Suppose a client sends:  GET /api/students/get/5

 The request goes through the following flow:


GET /api/students/get/5
        |
        v
StudentController
        |
        | getStudent(5)
        v
StudentService
        |
        | findByIdAndDeletedIsFalse(5)
        v
StudentRepository
        |
        v
Database


The result then travels back in the opposite direction:

Database -> Repository -> Service -> Controller -> HTTP Response

The controller is therefore responsible for converting the result of the service into an HTTP response.



 # 3\. StudentController

 The controller is marked with:   @RestController
 This tells Spring that this class handles REST API requests.


 The base URL is:   @RequestMapping("/api/students")
 Therefore, every endpoint inside this controller starts with:    /api/students

 For example:

@GetMapping("/get/{id}")    becomes:    GET /api/students/get/{id}



 # 4\. StudentService Dependency

 The controller has:
private StudentService studentService; and receives it through the constructor:

public StudentController(StudentService studentService){
    this.studentService=studentService;
}


 Spring creates the `StudentService` object and injects it into the controller.
 The controller therefore does not directly communicate with the database.

 Instead: Controller → Service → Repository

 This separation keeps responsibilities organized.



 # 5\. CREATE STUDENT

## Endpoint->    POST /api/students/create
 
## Controller Method

public ResponseEntity<Student> createStudent(@RequestBody Student student)

 ### What happens?

 The client sends student information in the request body.

 For example:

```
{
    "name": "Rahul",
    "age": 21,
    "rollNo": 10,
    "email": "rahul@example.com",
    "subject": "Java"
}
```

 `@RequestBody` tells Spring to convert the JSON request body into a `Student` object.

 The controller then calls:

```
studentService.createStudent(student);
```

---

 ## Service Method

```
public Student createStudent(Student studentRequest)
```

 The service first does:

```
studentRequest.setDeleted(false);
```

 This means a newly created student is considered active.

 Then:

```
Student studentResponse=studentRepository.save(studentRequest);
```

 The repository saves the student in the database.

 ### What does this method return?

 It returns:

```
Student
```

 Specifically, it returns the student object returned by:

```
studentRepository.save(...)
```

 The controller then puts that student into:

```
ResponseEntity<Student>
```

 and returns it to the client.

 # 6\. GET STUDENT BY ID

 ## Endpoint

```
GET /api/students/get/{id}
```

 Example:

```
GET /api/students/get/5
```

 ## Controller Method

```
public ResponseEntity<Student> getStudent(@PathVariable Long id)
```

 `@PathVariable` takes the `id` from the URL.

 For:

```
/api/students/get/5
```

 the value of `id` is:

```
5
```

 The controller calls:

```
studentService.getStudent(id);
```

---

 ## Service Method

```
public Student getStudent(Long id)
```

 The service calls:

```
studentRepository.findByIdAndDeletedIsFalse(id);
```

 This is important because the method searches for a student where:

```
id = requested ID
AND
deleted = false
```

 So a soft-deleted student should not be returned by this method.

 The repository returns an:

```
Optional<Student>
```

 An `Optional` represents the possibility that a student may or may not exist.

 The code checks:

```
if(student.isPresent()) return student.get();
```

 If the student exists, the actual `Student` object is returned.

 If the student does not exist:

```
return null;
```

---

 # 7\. How GET Handles Not Found

 The controller receives the result:

```
Student studentResponse=studentService.getStudent(id);
```

 It then checks:

```
if(studentResponse == null)
    return ResponseEntity.notFound().build();
```

 `ResponseEntity.notFound()` creates an HTTP:

```
404 Not Found
```

 response.

 Therefore:

```
Student exists
      ↓
Student object returned
      ↓
HTTP 200 OK
```

 Whereas:

```
Student doesn't exist
      ↓
Service returns null
      ↓
Controller detects null
      ↓
HTTP 404 Not Found
```

 There is no exception being thrown here.

 The application is handling the "not found" situation manually by checking whether the service returned `null`.

 ## Controller Method

```
public ResponseEntity<List<Student>> getStudent()
```

 This method returns a:

```
ResponseEntity<List<Student>>
```

 That means the response contains a list of students.

 The controller calls:

```
studentService.getAllStudent();
```

---

 ## Service Method

```
public List<Student> getAllStudent()
```

 The service calls:

```
studentRepository.findByDeletedIsFalse();
```

 This retrieves students whose:

```
deleted = false
```

 The returned value is:

```
List<Student>
```

 So multiple students can be returned.

---

 ## Not Found Handling

 The controller contains:

```
if(studentListResponse == null)
    return ResponseEntity.status(HttpStatus.NOT_FOUND).body(null);
```

 If the service returns `null`, the controller sends:

```
404 Not Found
```

 Otherwise:

```
return ResponseEntity.ok(studentListResponse);
```

 returns:

```
200 OK
```

 with the student list.

 An important point is that repository methods that return lists commonly return an empty list when there are no records rather than `null`.

 Therefore, with the current code, an empty database result may result in:

```
200 OK
[]
```

 rather than:

```
404 Not Found
```

 The code itself is not being changed here; this is simply how the current logic behaves depending on what the repository returns.

 # 10\. Update Service Flow

 The service first searches for the student:

```
Optional<Student> existingStudent=studentRepository.findById(id);
```

 Unlike the GET method, this uses:

```
findById(id)
```

 rather than:

```
findByIdAndDeletedIsFalse(id)
```

 The result is an:

```
Optional<Student>
```

 The code checks:

```
if(existingStudent.isEmpty()) return null;
```

 So if the student doesn't exist, the service returns:

```
null
```

 The controller then does:

```
if(studentResponse == null)
    return ResponseEntity.notFound().build();
```

 and sends:

```
404 Not Found
```

---

 # 11\. What Happens When the Student Exists During Update?

 The existing student is extracted:

```
Student studentToUpdate = existingStudent.get();
```

 Then the fields are updated:

```
studentToUpdate.setName(studentReq.getName());
studentToUpdate.setAge(studentReq.getAge());
studentToUpdate.setRollNo(studentReq.getRollNo());
studentToUpdate.setEmail(studentReq.getEmail());
studentToUpdate.setSubject(studentReq.getSubject());
studentToUpdate.setDeleted(false);
```

 The updated student is then saved:

```
return studentRepository.save(studentToUpdate);
```

 Therefore the service returns:

```
Student
```

 The controller returns:

```
200 OK
```

 with the updated student.

 # 13\. Hard Delete Service Method

 The service first checks whether the student exists:

```
Boolean studentExists=studentRepository.existsById(id);
```

 If the student doesn't exist:

```
if(!studentExists) return false;
```

 The controller receives `false` and returns:

```
ResponseEntity.notFound().build();
```

 Therefore:

```
Student doesn't exist
       ↓
existsById() = false
       ↓
Service returns false
       ↓
Controller returns 404
```

 If the student exists:

```
studentRepository.deleteById(id);
```

 deletes the record from the database.

 Then:

```
return true;
```

 is returned.

 The controller receives `true` and returns:

```
200 OK
```

 with:

```
Student deleted
```

---

 # 14\. Hard Delete vs Soft Delete

 There are two different deletion concepts in this application.

 ## Hard Delete

 The method:

```
deleteStudent()
```

 uses:

```
studentRepository.deleteById(id);
```

 The database record is actually deleted.

 Conceptually:

```
Before:

Student ID 5
deleted = false

        ↓ hard delete

After:

Student ID 5 does not exist
```

---

 ## Soft Delete

 The soft-delete method attempts to keep the database record but change:

```
deleted = false
```

 to:

```
deleted = true
```

 Conceptually:

```
Before:

Student ID 5
deleted = false

        ↓ soft delete

After:

Student ID 5
deleted = true
```

 The record remains in the database.

 This allows the application to retain the data while treating the student as deleted.

 # 16\. Important Note About the Current Soft Delete Method

 The current service code contains this logic:

```
Optional<Student> existingStudent =
        studentRepository.findByIdAndDeletedIsFalse(id);

if(!existingStudent.isEmpty()) return false;

Student studentToMarkDeleted=existingStudent.get();
```

 There is an important logical issue here.

 `isEmpty()` means that the student was **not found**.

 Therefore:

```
if(!existingStudent.isEmpty()) return false;
```

 means:

```
If the student DOES exist,
return false.
```

 But immediately after that, the code tries:

```
existingStudent.get();
```

 That creates a contradictory flow.

 The apparent intended flow is likely:

```
Student exists
     ↓
get student
     ↓
set deleted = true
     ↓
save student
     ↓
return true
```

 and:

```
Student doesn't exist
     ↓
return false
```

 However, the current code does not implement that intended flow correctly.

 This note is only documenting the behavior/logic of the provided code; the code itself has not been changed.

 # 17\. How `Optional` Is Being Used

 `Optional<Student>` appears in the service layer.

 For example:

```
Optional<Student> student=studentRepository.findByIdAndDeletedIsFalse(id);
```

 An `Optional` is useful when a database query may not return a record.

 There are two main possibilities:

```
Optional contains Student
```

 or:

```
Optional is empty
```

 The code uses:

```
student.isPresent()
```

 to check whether a value exists.

 It also uses:

```
existingStudent.isEmpty()
```

 to check whether no value exists.

 Finally:

```
existingStudent.get()
```

 extracts the `Student` from the `Optional`.

 # 18\. How 404 Not Found Is Handled

 The application currently does not use a custom exception handler for these cases.

 Instead, the service communicates failure using:

```
null
```

 or:

```
false
```

 The controller then converts that result into an HTTP 404 response.

 There are two patterns.

 ## Pattern 1 — Service returns `null`

 Used by methods returning a `Student`.

 Example:

```
Service
   ↓
Student found → Student object
Student absent → null
```

 Controller:

```
Student object → 200 OK
null → 404 Not Found
```

 This occurs in:

```
getStudent()
```

 and:

```
updateStudent()
```

---

 ## Pattern 2 — Service returns `false`

 Used by methods returning a `Boolean`.

 Example:

```
Service
   ↓
Operation successful → true
Student doesn't exist → false
```

 Controller:

```
true → 200 OK
false → 404 Not Found
```

 This occurs in:

```
deleteStudent()
```

 and is intended for:

```
deleteStudentSoftly()
```

---

 # 19\. What `ResponseEntity` Does

 The controller methods return `ResponseEntity`.

 For example:

```
ResponseEntity<Student>
```

 means the HTTP response contains a `Student`.

 `ResponseEntity` allows the controller to control:

 - HTTP status code
- response body
- response headers, if required

 Examples from the code:

 ### Successful response

```
ResponseEntity.ok(studentResponse)
```

 means:

```
HTTP 200 OK
Body: studentResponse
```

 ### Not found

```
ResponseEntity.notFound().build()
```

 means:

```
HTTP 404 Not Found
Body: empty
```

 ### Custom status

```
ResponseEntity.status(HttpStatusCode.valueOf(200))
```

 creates a response with HTTP status:

```
200 OK
```
